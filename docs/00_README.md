# B2B Bounty Marketplace — Vibecoding Pack

## Что строим

Marketplace, где бизнес публикует bounty за состоявшуюся квалифицированную B2B-встречу, а SDR / аутричеры / sales-менеджеры выбирают bounty, назначают встречи и получают фиксированное вознаграждение после подтверждения результата.

Главная единица продукта в MVP: **qualified attended meeting**.

Не строим в MVP:
- собственную видеосвязь;
- автоматический AI-анализ звонков;
- сложный matching SDR ↔ bounty;
- SQL / revenue-share bounty;
- полноценный escrow внутри собственного банковского контура;
- встроенный email/Telegram/LinkedIn sender;
- сложную антифрод-модель;
- мобильные приложения.

## Рекомендуемый стек

- Frontend + backend application layer: Next.js + TypeScript.
- UI: Tailwind CSS + shadcn/ui.
- Database/Auth/Storage: Supabase.
- Hosting: Vercel.
- Notifications: Telegram Bot API.
- Emails: Resend или аналог.
- Analytics: PostHog или простая event-таблица на MVP.
- Payments:
  - Sprint 1–2: ручной депозит + внутренний ledger.
  - После юридической и провайдерской проверки: интеграция решения типа «Безопасной сделки»/marketplace payments.
- AI: OpenAI API только для модерации/обогащения bounty после того, как базовый workflow работает.

## Главный принцип vibecoding

Не просить модель «сделай весь marketplace». Давать ей маленькие вертикальные задачи:
1. schema;
2. auth;
3. конкретная страница;
4. конкретный workflow;
5. тесты;
6. только потом следующий workflow.

Каждый этап должен заканчиваться работающим приложением.

## Порядок работы

1. Создай новый GitHub-репозиторий.
2. Создай Next.js приложение.
3. Подключи Supabase.
4. Положи документы из этого пакета в `/docs`.
5. Перед началом каждой сессии давай AI:
   - `01_PRD.md`
   - релевантный flow из `03_USER_FLOWS.md`
   - `02_DATA_MODEL.md`
   - конкретную задачу из `07_MVP_BACKLOG.md`
6. Не разрешай AI менять scope без явного объяснения.
7. После каждого законченного блока:
   - запусти typecheck;
   - lint;
   - тесты;
   - вручную проверь happy path;
   - commit.

## Definition of Done MVP

MVP считается готовым, когда можно пройти путь:

**Admin создаёт бизнес → публикует bounty → SDR регистрируется → берёт bounty → регистрирует prospect → передаёт назначенную встречу → бизнес вносит/подтверждает депозит → встреча становится due → бизнес принимает или оспаривает → admin решает dispute → SDR получает статус payout due → рейтинги/статистика обновляются.**

На первом пилоте деньги можно фактически переводить вручную, а система должна вести неизменяемый журнал финансовых событий.
